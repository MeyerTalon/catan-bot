# AWS infrastructure (Terraform)

Runs the Catan app on AWS: Cognito for auth, ECS Fargate for the API, RDS Postgres, and S3 + CloudFront for the static frontend.

```
Internet
  ├─ CloudFront ──▶ S3 (Vite build)                       modules/static-site
  └─ ALB ────────▶ ECS Fargate (FastAPI) ──▶ RDS Postgres  modules/backend-service, modules/database
                       │  DATABASE_URL from Secrets Manager
                       └─ Cognito user pool (sign-up / login / refresh)  modules/auth
```

Idle cost with the prod defaults is roughly **$30–45/month** (ALB + `db.t4g.micro` + one Fargate Spot task). No NAT gateway by default; tasks run in public subnets with public IPs and RDS sits in private subnets.

## Layout

```
terraform/
├── bootstrap/          one-time per AWS account: state bucket, GitHub OIDC provider, Terraform CI roles (local state)
├── modules/            reusable building blocks, no environment knowledge
│   ├── network/        VPC, public + private subnets, optional NAT
│   ├── database/       RDS Postgres + Secrets Manager secret with DATABASE_URL
│   ├── auth/           Cognito user pool + app client
│   ├── backend-service/ ECR, ECS Fargate service, ALB, IAM, logs, autoscaling
│   ├── static-site/    S3 + CloudFront (OAC, SPA fallback)
│   └── deploy-role/    least-privilege GitHub Actions role for app deploys
├── envs/
│   └── prod/           composes the modules; sizing lives in locals; remote state
├── Makefile            init/plan/apply/check wrappers (`mise run tf:*` from repo root)
└── .tflint.hcl
```

Three kinds of stack, three lifecycles:

| Stack | State | Applied by | Changes |
|---|---|---|---|
| `bootstrap/` | local file | a human, once | almost never |
| `envs/<env>/` | S3 (`bootstrap` bucket) | CI on `main`, or a human | whenever infra changes |
| app code | n/a | CI via `deploy-role` | every merge |

Secrets never live in `.tfvars` or git: the only secret (the RDS password) is generated by Terraform and stored in Secrets Manager; Cognito pool/client IDs are plain env vars. Remote state is encrypted and versioned, and it does contain the RDS password — treat bucket access as production access.

## Prerequisites

- Terraform **>= 1.10** and **tflint** via mise (`mise install` at the repo root)
- AWS CLI with credentials for an IAM user/role that can create the resources (`AdministratorAccess` is fine for the first apply). Credentials go in `~/.aws/credentials` or env vars — never in the repo. Confirm with `aws sts get-caller-identity`.
- Docker (to build the backend image)

## First-time setup

### 1. Bootstrap the account

```bash
cd terraform/bootstrap
cp terraform.tfvars.example terraform.tfvars   # set github_repository, or comment it out
terraform init
terraform apply
```

Creates the state bucket (`catan-terraform-state-<account-id>`), the GitHub OIDC provider, and two roles for Terraform CI (`catan-terraform-plan`, `catan-terraform-apply`). Keep `bootstrap/terraform.tfstate` somewhere safe (it holds no secrets, but losing it means importing these resources later).

### 2. Point the environment at the bucket

Edit `envs/prod/backend.hcl` and replace `<ACCOUNT_ID>` with the value from `terraform output state_bucket`. Commit it — it contains nothing secret.

### 3. Create the environment (two passes)

ECS cannot start until an image exists, so create the registry first:

```bash
cd terraform
make init ENV=prod
terraform -chdir=envs/prod apply -target=module.backend.aws_ecr_repository.this
```

Build and push the backend image from the repo root:

```bash
ECR=$(terraform -chdir=terraform/envs/prod output -raw ecr_repository_url)
aws ecr get-login-password --region us-west-2 | docker login --username AWS --password-stdin "${ECR%%/*}"
docker build --platform linux/amd64 -f backend/Dockerfile -t "$ECR:latest" backend
docker push "$ECR:latest"
```

Then the rest (RDS takes several minutes):

```bash
make plan ENV=prod
make apply ENV=prod
```

The first deployment comes up with an empty database; `/health` passes regardless, so apply the schema next.

### 4. Apply the schema

RDS is in private subnets, so migrations run *inside* the VPC as a one-off ECS task using the backend image (which has Alembic and the `db/` revisions):

```bash
OUT="terraform -chdir=terraform/envs/prod output -raw"
aws ecs run-task \
  --cluster "$($OUT ecs_cluster_name)" \
  --task-definition "$($OUT backend_task_definition_family)" \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=$(terraform -chdir=terraform/envs/prod output -json backend_task_subnet_ids | tr -d ' '),securityGroups=[$($OUT backend_security_group_id)],assignPublicIp=ENABLED}" \
  --overrides '{"containerOverrides":[{"name":"app","command":["sh","-c","cd /app && alembic -c db/alembic.ini upgrade head"]}]}'
```

Watch it in the `log_group_name` output. `db/` stays the schema source of truth; see `db/README.md`. This requires the backend image to contain `db/` and Alembic — `backend/Dockerfile` currently copies only `app/`, so add `db/` to the image (or build from the repo root) before relying on this. (Running Alembic from a laptop or a GitHub runner only works if you add a NAT-free path into the VPC, e.g. an SSM bastion — not provided here.)

### 5. Confirm the backend is healthy

```bash
curl "$($OUT backend_url)/health"
```

If the first deployment rolled back before the schema existed, roll it again:

```bash
aws ecs update-service \
  --cluster "$($OUT ecs_cluster_name)" --service "$($OUT ecs_service_name)" --force-new-deployment
```

### 6. Build and publish the frontend

Vite bakes env vars at build time. From the repo root:

```bash
export VITE_BACKEND_URL="$(terraform -chdir=terraform/envs/prod output -raw backend_url)"
mise run fe:build
aws s3 sync frontend/dist "s3://$(terraform -chdir=terraform/envs/prod output -raw frontend_bucket)" --delete
aws cloudfront create-invalidation \
  --distribution-id "$(terraform -chdir=terraform/envs/prod output -raw cloudfront_distribution_id)" --paths "/*"
```

Open `terraform -chdir=terraform/envs/prod output -raw frontend_url`.

### 7. Wire up GitHub Actions

Two workflows, two roles, no long-lived AWS keys — every role is assumed via OIDC and trusts only this repository (and only `main` for anything that writes).

**`.github/workflows/terraform.yml`** (infra) reads these **repository variables**; an unset variable simply skips that job:

| Variable | Value from | Used for |
|---|---|---|
| `AWS_TERRAFORM_PLAN_ROLE_ARN` | `bootstrap` output `terraform_plan_role_arn` | `terraform plan` on pull requests |
| `AWS_TERRAFORM_APPLY_ROLE_ARN` | `bootstrap` output `terraform_apply_role_arn` | `terraform apply` on `main` |

**`.github/workflows/ci-cd.yml`** (app deploy on `main`) reads these **repository secrets**:

| Secret | Value from `envs/prod` output |
|---|---|
| `AWS_ROLE_ARN` | `github_deploy_role_arn` |
| `AWS_REGION` | `us-west-2` (matches `local.aws_region`) |
| `ECR_REPOSITORY` | `ecr_repository_url` |
| `ECS_CLUSTER` | `ecs_cluster_name` |
| `ECS_SERVICE` | `ecs_service_name` |
| `FRONTEND_BUCKET` | `frontend_bucket` |
| `CLOUDFRONT_DISTRIBUTION_ID` | `cloudfront_distribution_id` |
| `VITE_BACKEND_URL` | `backend_url` |

The deploy role can push images, roll the service, run one-off tasks from the backend task definition (migrations), and sync the frontend — nothing else. Note the migration caveat in step 4: a runner cannot reach RDS directly, so the migration step in `ci-cd.yml` needs to go through `aws ecs run-task` (the role already allows it) rather than running Alembic on the runner.

## Day-to-day

```bash
cd terraform
make check                 # fmt -check + validate every stack/module (no AWS access needed)
make lint                  # tflint (optional)
make plan ENV=prod         # writes envs/prod/tfplan
make apply ENV=prod        # applies that plan
make output ENV=prod ARGS="-raw backend_url"
```

Deploy new backend code without touching Terraform: push a new `:latest` image and run `aws ecs update-service --force-new-deployment` (this is what `ci-cd.yml` does). For reproducible deploys, push an immutable tag (e.g. the git sha) as well and run `make plan ENV=prod ARGS="-var backend_image_tag=<git sha>"`.

Shell into a running task for debugging: set `enable_execute_command = true` on `module.backend`, apply, then `aws ecs execute-command --cluster ... --task ... --container app --interactive --command /bin/sh`.

## Adding an environment

1. `cp -r envs/prod envs/staging`
2. In `envs/staging/main.tf` change `environment = "staging"` and shrink the sizing (e.g. `backup_retention_days = 1`, `deletion_protection = false`, `skip_final_snapshot = true`, `max_count = 1`).
3. In `envs/staging/backend.hcl` set `key = "envs/staging/terraform.tfstate"`.
4. `make init ENV=staging && make plan ENV=staging`.
5. Add the env to the matrix in `.github/workflows/terraform.yml`.

Every environment is an independent state file and VPC; nothing is shared except the bootstrap bucket and the OIDC provider.

## Custom domains / HTTPS

- **API**: request an ACM certificate in `us-west-2`, set `backend_certificate_arn` in `envs/prod/main.tf`, and CNAME your hostname to `alb_dns_name`. Port 80 then redirects to 443.
- **Site**: request an ACM certificate in **`us-east-1`** (CloudFront requirement), set `frontend_certificate_arn` and `frontend_domain_names`, and CNAME to `distribution_domain_name`.

## Destroy

```bash
cd terraform
make destroy ENV=prod
```

Prod defaults protect data: `deletion_protection = true` and `skip_final_snapshot = false` on RDS, `deletion_protection = true` on the Cognito pool (every user lives there), `force_destroy = false` on the frontend bucket. Flip those in `envs/prod/main.tf`, apply, then destroy. Bootstrap's state bucket has `prevent_destroy`; empty and delete it by hand if you are leaving the account.
